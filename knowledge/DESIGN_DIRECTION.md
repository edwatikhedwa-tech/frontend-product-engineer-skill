# Design Direction

This is the concrete artifact produced by the Design Director. For CREATE and systemic REDESIGN, write it before substantial implementation. For EXTEND, write the proportional compatibility version described in `knowledge/DESIGN_DIRECTOR.md`.

## Required direction

- product personality and emotional target;
- one-paragraph visual identity statement;
- visual thesis: why this language fits the product, user, and job;
- visual hierarchy and reading order;
- spatial/compositional strategy and intentional density;
- density target for the task (calm, balanced, or information-rich);
- typography roles and line-length rule;
- surface, border, radius, elevation, and color principles;
- navigation and interaction character;
- responsive strategy and key breakpoints;
- state and motion principles;
- selected reference categories and synthesis into a new system;
- three signature decisions that make the product recognizable;
- deliberate exclusions: generic or decorative treatments rejected;
- explicit do/don’t examples.

## Design rationale

For each large decision, record:

| Product/user/task reason | Design principle | Concrete decision | Expected behavior/evidence |
| --- | --- | --- | --- |
|  |  |  |  |

Avoid “modern”, “clean”, “premium”, “looks good”, and library defaults as standalone rationale. Explain the product consequence.

## Acceptance criteria

The first rendered slice must demonstrate the direction in composition, typography, surfaces, navigation, data presentation, and at least one meaningful state. The Design Director then checks the anti-generic gate and asks whether this is the best interface the product could reasonably have within its constraints.

Use tokens and component principles to make the direction executable. A design direction is not a moodboard, a list of colors, or a substitute for product decisions.
